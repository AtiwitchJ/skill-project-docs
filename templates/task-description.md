# Task Description drafting worksheet

Use with the existing Task owner and `rules/task-descriptions.md`. This worksheet is not a replacement for the project's approved tracker headings. Remove drafting instructions before publication. Write in the project's configured language and retain established Task number/UID/topic.

| Question | Sourced content to establish |
|---|---|
| Why this work? | Problem/gap and the decision it supports |
| What work and deliverable? | Concrete change, boundaries and output |
| Who uses the result, for what? | Named consumer/related Task and supported comparison/decision |
| How is it checked? | Real method, acceptance criterion and actual evidence or pending execution |
| Which sources / where? | Source plan/topic, artifact paths, report/raw-data links and relevant version |
| Who / when, if known? | Recorded ownership/review and actual work/test date; unresolved facts remain explicit |

## Planned versus observed

For an open Task, state expected deliverable and verification method. For completed work, distinguish the produced artifact, observed result, conclusion actually supported and remaining limitations. Synthetic samples, mock permissions, AI-drafted answers and unavailable expert review must be labelled. Missing evidence is not a passing result.

## Map into the project's existing format

Map purpose and actual/planned work into the approved work section; place outputs/links and results/limits under the corresponding approved sections. Keep Picture/How-to-read/Files or other required sections when present. Do not add a second summary merely to expose Wh labels. If bilingual content is required, pair equivalent meaning and limitations with identical numbers/IDs/paths in the required language order.

Prepare the exact before/after change and preserve unique existing text/images/links. A draft is not a live tracker update. Authorized remote edits require concurrency protection, readback and separately reported UI verification.
